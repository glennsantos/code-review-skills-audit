Code review skills: what we have, what is missing

Every code-review skill, agent, command and hook installed on one engineer's workstation, read in full and compared on the capabilities a complete review needs. Fourteen tools, one conclusion: every capability exists somewhere, and no tool has more than a third of them.

The one-paragraph answer

The rubric is best in agent-skills, the false-positive control is best in Anthropic's code-review plugin, the synthesis and dismissal discipline is best in pstack interrogate, the evidence standard is best in pstack blast-radius, the outward-facing writing is best in the personal pr-review, and the only tool that knows what actually breaks in our repos is a bmad override that loads a per-repo file of empirically verified defect classes.

Nothing runs the code. Nothing checks the API/UI contract mechanically, even though contract mismatch is our single largest verified defect class. Nothing learns from review outcomes. Nothing runs in CI on the main product repos. Nothing is evaluated. And the installs are drifting: three copies of the thermo-nuclear quality rubric, two versions of pr-review, two empty defect-review directories, one defect-class file that no skill loads.

Per-family assessment

agent-skills fork: code-review-and-quality

Strengths

  • The most complete written rubric in the set. It encodes review culture, not just bug-finding: the "improves overall code health" approval standard, the facts > style guide > design > consistency hierarchy for disagreements, and "don't accept I'll clean it up later".
  • Structural remedies are named moves (replace a conditional chain with a dispatcher, delete a pass-through wrapper, make a type boundary explicit), so a finding proposes the fix.
  • Change sizing with concrete thresholds (100 / 300 / 1000 changed lines, ~1000-line files) and four splitting strategies.
  • A dependency-upgrade review workflow (changelog, one package per change, lockfile diff) that no other tool has.
  • Severity prefixes separate required from optional so authors don't treat every comment as mandatory.
  • The only family with an eval harness: structural, trigger-routing and behavioral tiers, with a real fixture (SQL injection plus log injection in a user-search endpoint).
  • Portable across Claude Code, Cursor, Gemini, Codex and Copilot.

Missing

  • No procedure for acquiring the diff. /review says "staged or recent commits"; no PR number, branch or path handling.
  • No verification step. Findings are asserted against the diff; nothing says trace the call chain, check the caller, or run anything. "Verify the verification" is about the author's story, not the reviewer's.
  • No false-positive control: no confidence gate, no validation pass, no pre-existing-vs-introduced rule, no finding cap. A checklist this long pulls toward nit-heavy output despite the "lead with what matters" paragraph.
  • The multi-model review pattern is a diagram, never operationalized.
  • No GitHub posting, no verdict beyond a checkbox, no idempotency.
  • Taxonomy drift inside the repo: the skill and persona use Critical / Required / Optional / Nit / FYI; commands/review.toml and .claude/commands/review.md say Critical / Important / Suggestion.
  • Review speed and disagreement handling are human-team concerns that cost context every invocation without changing agent behaviour.
  • One behavioral eval case.

pstack: interrogate, blast-radius, no-comments, babysit triage, shipping

Strengths

  • interrogate has the best synthesis design here: state the intent, spawn read-only reviewers with one rubric, weight consensus, then apply lead judgment with named filters (nitpick gravity, hypothetical vs actual, premature abstraction, "I would have done it differently", missing-context signals). The Dismissed section is explicitly a trust mechanism.
  • Its rubric adds what others miss: idempotency ("what if it runs twice or crashed halfway"), structural vs conventional serialization of shared state, root cause vs symptom with an instruction to read callers and types, and security findings only when the input path is traced.
  • blast-radius is the only tool whose deliverable is proof. Five rungs (said so, pointed at the line, walked the bad case, ran it, reproduced in the app); anything below rung 4 is written up as unproven.
  • no-comments is the only lens on lint and TypeScript suppressions, and it asks whether a "do not remove" comment should be a type, a test or a lint rule.
  • bugbot-triage.md is the only artifact handling the inbound half: fix / dismiss / ask, ask-by-default for security, auth, billing and migrations, and a learned-pattern format with confidence levels.
  • The shipping playbook separates author from judge and posts verdicts on the PR so the record outlives the chat.

Missing

  • interrogate's premise, model diversity, is degraded here: the Agent tool accepts only Claude models, so the panel has correlated blind spots. Context diversity (blind vs contextual vs consumer-side), which bmad does, would be the substitute, and interrogate does not do it.
  • No GitHub posting, no verdict, no idempotency. Terminal-only deliverable.
  • Reviewers can read but are not told to run anything; the evidence ladder lives in blast-radius, not in the reviewer prompt.
  • No repo-specific priors loaded into reviewers.
  • All carry disable-model-invocation: true; they never fire unless typed.
  • Babysit, shipping and the watcher are bound to Graphite, Cursor Bugbot and bun scripts. The triage rubric is reusable; the mechanics are not.
  • No evals. The code-quality lens is a near-copy of thermo-nuclear-code-quality-review, so that rubric now lives in three installed places.

Anthropic code-review plugin and feature-dev:code-reviewer

Strengths

  • The best false-positive pipeline: an explicit do-not-flag list (pre-existing, linter-catchable, silenced by lint-ignore, "looks like a bug but is correct", pedantic nitpicks), a validation subagent per finding, and CLAUDE.md violations must quote the exact rule.
  • Idempotent: skips closed, draft, trivial and already-reviewed PRs.
  • Cheap by construction: haiku prechecks, sonnet compliance and summary, opus only for bug hunting and validation.
  • One GitHub comment with full-SHA permalinks and a line of context, which renders correctly.
  • One bug agent is deliberately diff-only and the other reads changed code, a small context-diversity trick.

Missing

  • Scope is bugs plus CLAUDE.md compliance. Security, test coverage and quality are excluded "unless explicitly required in CLAUDE.md", so CLAUDE.md becomes the only place for repo priors, and ours is a project guide, not a defect list.
  • PR only. Cannot review a working tree or branch before the PR exists.
  • Summary comment, not inline; no verdict line.
  • README and command have drifted: the README promises a 0–100 confidence score with an 80 threshold and a git-blame history agent; the command implements neither.
  • feature-dev:code-reviewer runs on sonnet by default, reviews unstaged changes only, and posts nothing.

Built-in code-review, simplify, security-review

Strengths

  • The effort dial (low and medium: fewer, high-confidence findings; high to max: broader coverage), inline --comment, --fix, and typed ReportFindings that the IDE renders.
  • simplify is scoped to quality only and says so.

Missing

  • Source is not inspectable, so it cannot be customized with defect classes, verdict lines or posting format, and cannot be put under evals. Treat it as a baseline to compare against, not a thing to build on.

thermos and cursor-team-kit

Strengths

  • thermo-nuclear-review carries two lenses nobody else has: breaking developer experience (env var renames, port remaps, new required scripts) and feature-flag leaks. Its "intended breakage" and over-reporting paragraphs are well calibrated.
  • It reads the PR discussion only after its own audit, so it has fresh eyes and can then attribute Bugbot findings.
  • verify-this gives a verdict vocabulary for evidence: VERIFIED / NOT VERIFIED / INCONCLUSIVE with baseline and treatment captured the same way.
  • make-pr-easy-to-review and pr-review-canvas cover the author side and the human walkthrough, which no other family does.

Missing

  • thermo-nuclear-review defines no output format, no severity taxonomy and no posting. It is a prompt, not a workflow.
  • The parent must gather the diff and file contents; the subagent cannot start from a PR number.
  • The quality rubric is duplicated identically in thermos, cursor-team-kit and pstack.
  • review-and-ship commits and opens the PR in the same flow as the review, so reviewer and author are the same agent, which the pstack shipping playbook explicitly forbids.

bmad-code-review and the workspace overrides

Strengths

  • The only tool with a spec-conformance layer (Acceptance Auditor checks the diff against the story's acceptance criteria) and the only one integrated with the story lifecycle.
  • Context diversity by design: Blind Hunter gets the diff and nothing else, Edge Case Hunter gets diff plus repo, Acceptance Auditor gets diff plus spec. Under Claude-only models this is the right substitute for model diversity.
  • Action-oriented triage: decision-needed / patch / defer / dismiss, with defer for pre-existing issues.
  • The customization surface is what made our best review tooling possible. persistent_facts loads defect classes derived from an LLM classification of every fix deploy over a six-month window. on_complete posts an auditable comment with a VERDICT line to the issue and PR, with a disk fallback, and refuses to post to a guessed issue number.
  • The needs-human-review tier (auth, config, migrations, integrations, or more than 400 changed lines) fires regardless of findings.

Missing

  • Blind Hunter is told to "find at least ten issues" and to HALT on zero findings as "suspicious". This manufactures findings and contradicts the override's "a style nit is never a finding". Nothing downstream validates them.
  • Edge Case Hunter is forbidden from reading beyond the diff, so its unhandled-path findings are hypotheticals the triage step dismisses by hand.
  • No validation pass between layers and triage; dedupe and classify only.
  • Interactive HALTs at every step make it unusable in CI or a loop. The non-interactive story-automator variant exists in only about half the repos.
  • Heavy activation ceremony: a python resolver, config.yaml, greeting the user in the configured language.
  • Uneven coverage. Defect classes and the posting hook are wired in six repos. One repo has a defect-class file but no toml override, so the skill never loads it. Two repos have defect-review directories with no SKILL.md.
  • The defect classes are a snapshot, regenerated by hand, with no feedback from review outcomes.

Personal and shared: pr-review, issue-review, defect-review

Strengths

  • pr-review has the best outward-facing discipline: a must-fix-only bar with a named exclusion list, a mandatory verify-before-posting step, inline comments via the review API, consequence-first plain language ("the code does / so / when"), jargon glossed inline, evidence in a collapsed block, at most five findings, comments only.
  • defect-review is a good self-contained pattern: priors, tier, auditable comment, disk fallback, in sixty lines.

Missing

  • pr-review is single-pass and single-lens: no parallel reviewers, no consensus, no repo priors, no test run, no verdict, no idempotency (re-running posts duplicates), PR only.
  • The personal copy and the team plugin copy have drifted: the plugin version, which the team installs, lacks the entire plain-language writing section.
  • issue-review hardcodes one repo and a specific review-plan document, and calls bmad-code-review inside a non-interactive flow that bmad will HALT.

Available but not installed

  • pr-review-toolkit provides the two lenses most aligned with the verified defect classes and absent everywhere else: silent-failure-hunter (fail-open error handling is a named class in three repos) and pr-test-analyzer (behavioural coverage gaps rated 1–10). Also type-design-analyzer and comment-analyzer.
  • claude-security does a threat-model-first scan of a diff with independent verification and patch generation. Heavy, but the only deep security option beyond regex hooks and checklists.
  • security-guidance is installed and useful, but its agentic commit reviewer does not read the org policy file; only the Stop-hook review does.

Gaps no tool fills

  1. No end-to-end flow.

    Priors, layered fan-out, per-finding validation, evidence by execution, plain-language inline posting, verdict, idempotency: each exists once, none exist together.

  2. Nothing runs the code.

    Only blast-radius (one fact) and verify-this (one claim) execute anything. No review skill runs the affected tests, checks CI status, or reproduces a claimed bug before posting it.

  3. No mechanical contract check.

    Contract mismatch between the API and the UI is our largest verified defect class. It appears only as prose ("grep the UI repo for the endpoint path"). No step diffs a response model against the hook that reads it.

  4. No learning loop.

    Accepted and dismissed findings, and post-merge fixes, never flow back into the defect classes. bugbot-triage.md has the right learned-pattern format, but it is Cursor-bound and unused here.

  5. No evals for anything we rely on.

    agent-skills has the harness; pr-review, defect-review, the bmad override and interrogate have zero cases. We already hold a classified corpus of past fix diffs that would make a regression suite: does the reviewer catch the class of bug that actually shipped?

  6. No CI trigger where it matters.

    Required status checks are unavailable on our GitHub plan and most PRs in some repos merge unreviewed. claude-code-action review exists only on two smaller repos. The main product repos have none.

  7. No incremental review.

    Only the Anthropic plugin skips an already-reviewed PR; nothing reviews just the commits since the last review comment.

  8. No GitHub inbound triage.

    Reply-with-disproof, resolve-thread, and ask-by-default categories exist only in the Graphite-bound babysit playbook.

  9. Seven severity vocabularies.

    Critical/Required/Nit/Optional/FYI; Critical/Important/Suggestion; critical/warning/nit; Act on/Consider/Noted/Dismissed; decision-needed/patch/defer/dismiss; fix/dismiss/ask; merge-ready/needs-changes/needs-human-review. A reader of two reviews cannot compare them.

  10. Front-end lenses are prose only.

    React Query invalidation under an infinite staleTime, effect cleanup, and the design-system guardrail are listed in the UI repo's defect classes; no review step runs the guardrail script or enumerates a mutation's invalidation set.

  11. Human handoff is not wired.

    needs-human-review is a verdict string; bmad-checkpoint-preview and pr-review-canvas exist to produce a human walkthrough and nothing invokes them when that verdict fires.

  12. Drift and dead installs.

    Three copies of the quality rubric; two versions of pr-review; two empty defect-review directories; one unwired defect-class file; one command with hardcoded repo paths.

Recommendations, in priority order

  1. Build one workspace review skill in the team plugin from the best parts.

    bmad-style layered fan-out (blind / contextual with defect classes / consumer-contract / spec-AC when a story exists), then per-finding validation subagents (Anthropic pattern), then lead judgment with a Dismissed section and a finding cap (interrogate), then consequence-first inline comments plus a VERDICT line (pr-review and defect-review), then skip if already reviewed at this SHA. Drop the "at least ten findings" mandate. Non-interactive by default.

  2. Fix the installs this week.

    Sync the plugin pr-review with the personal copy. Wire the orphaned defect-class file through a bmad-code-review.toml. Delete or fill the empty defect-review directories. Remove two of the three quality-rubric copies. Retire or generalize issue-review.

  3. Add a contract-check step between the API and the UI.

    For each changed response model, locate the hook that reads the endpoint and compare field names, casing and wrapper keys. The single highest-leverage automation given the defect mix.

  4. Put the skill in CI with claude-code-action on pull_request for the main product repos.

    It cannot block on our plan, but for most PRs it will be the only review that happens.

  5. Install pr-review-toolkit or fold silent-failure-hunter and pr-test-analyzer into the fan-out.

    Both map to verified defect classes.

  6. Adopt the evidence standard.

    Any needs-changes finding must reach rung 3 of the blast-radius ladder (walked the failing case) and say which rung it reached; anything at rung 1 or 2 is Consider, not Act on.

  7. Stand up evals on the agent-skills harness.

    Use real past fix diffs as fixtures, graded on "flags the class that shipped" and "posts at most five findings". Regenerate defect classes on a schedule and record the window in the file.

  8. Unify the vocabulary.

    One severity set and one verdict line across the plugin skill, the bmad override and defect-review.

  9. Port bugbot-triage.md to GitHub threads as the inbound half.

    fix / dismiss-with-disproof / ask, ask-by-default for auth, billing, migrations and data.

  10. Contribute back to the agent-skills fork.

    A scope-acquisition procedure, a validation pass and false-positive list, a finding cap, the idempotency rule, and a fix for the Critical/Important/Suggestion drift in the two review commands. Its eval harness is the right place to prove each of those helps.
